## ٣. المشاكل المكتشفة (Bugs)

### 🔴 BUG-1 (الأهم) — قائمة العهد في فورم المصروف مش بتتحدث (ستالة)

| | |
|---|---|
| **الخطورة** | عالية (تعطّل وظيفة) |
| **المكان** | `src/FastCom.Client/Pages/ExpenseForm.razor` — دالة `OnTripChanged` **سطر 1932** و `LoadCustodiesAsync` **سطر 1946-1951** |

**الوصف:** في فورم المصروف خطوة «٣ الربط»، بعد اختيار الرحلة تظهر الرسالة **«مافيش عهد مفتوحة على الرحلة دي»** رغم إن العهدة `CUS-2026-000001` موجودة ومفتوحة على نفس الرحلة. القائمة (اللي فيها العهدة) مش بتظهر غير بعد تفاعل عشوائي تاني (زي تبديل بين الخطوات).

**إعادة الإنتاج:**
1. افتح تعديل أي مصروف → خطوة «٣ الربط».
2. اختار الرحلة `TR-2026-000006`.
3. **متوقع:** ظهور قائمة فيها `CUS-2026-000001` — **فعلي:** رسالة «مافيش عهد مفتوحة».

**الدليل (API سليم، المشكلة في الواجهة):**
```
GET /api/options/custodies?tripId=14  →  200
[{"id":7,"label":"CUS-2026-000001","ownerType":"Driver","ownerId":2,"tripId":14,"amountIssued":500.0000}]
```
(المصدر: `OptionsController.cs:201-210` — الفلتر `Status != "Closed" && != "Approved"` صحيح.)

**السبب الجذري:**
```csharp
private void OnTripChanged(ChangeEventArgs e)      // سطر 1928 — handler متزامن (void)
{
    _f.TripId    = ...;
    _f.CustodyId = null;
    _ = LoadCustodiesAsync();                       // 🔴 سطر 1932 — fire-and-forget
}
```
1. الـ handler متزامن، فـ Blazor يعمل re-render فورًا **قبل** ما الرد يوصل → يعرض القائمة القديمة (فارغة).
2. لما الرد يوصل و `_custodies` يتملي، **مفيش `StateHasChanged`** → الشاشة بتفضل على القديم لحد حدث تاني.
3. لو المستخدم بدّل الرحلة بسرعة، ردَّان في نفس الوقت والأخير يفوز بدون حارس ترتيب → رد فاضي ممكن يلغي رد فيه بيانات.
4. مضاعف: `SafeGetT` (سطر 2036-2040) بيلتهم أي خطأ ويرجّع `new()` فـ أي فشل هدوء بيظهر نفس الرسالة الغلط.

**الإصلاح المقترح:**
```csharp
private async Task OnTripChanged(ChangeEventArgs e)   // async Task → Blazor يعمل re-render بعد الاكتمال
{
    _f.TripId    = long.TryParse(e.Value?.ToString(), out var t) && t > 0 ? t : null;
    _f.CustodyId = null;
    await LoadCustodiesAsync();
}
```
+ إضافة حارس ترتيب (مثلاً `CancellationTokenSource` لكل تغيير يُلغى السابق)، + عدم ابتلاع الأخطاء صامتًا في `SafeGetT` (على الأقل log).

### 🟡 BUG-2 — تسريب ترجمة إنجليزي `(Started)` في قائمة رحلات العهد

| | |
|---|---|
| **الخطورة** | متوسطة (ظاهرة) |
| **المكان** | `src/FastCom.Client/Pages/Custodies.razor` — دالة `TripStatusAr` **سطر 3139-3147** |

**الوصف:** في فورم العهد الجديد، خيارات قائمة الرحلة بتظهر: `TR-2026-000006 — هيثم الوضيف (Started)` بدل `(في الطريق)`.

**السبب الجذري:**
```csharp
private static string TripStatusAr(string s) => s switch
{
    "Planned"   => "مخططة",
    "Assigned"  => "متسندة",
    "InTransit" => "في الطريق",   // ⚠️ القيمة دي مش بتستخدم أصلًا!
    "Completed" => "مكتملة",
    "Cancelled" => "ملغية",
    _           => s              // 🔴 "Started" بيقع هنا ويطلع بالإنجليزي
};
```
حالة الرحلة بعد التشغيل القيمة الحقيقية ليها **`"Started"`** (بتتحط في `TripsController.cs:414`)، والدالة مكتوبة لقيمة `InTransit` الغير موجودة. أما `Trips.razor` و `TripForm.razor` فعندهم `"Started" => "في الطريق"` صح — يعني الصفحة الوحيدة الناقصة هي دي.

**الإصلاح المقترح:** إضافة `"Started" => "في الطريق",` (وترشيح إزالة `InTransit` أو إبقاؤها للمستقبل).

### 🟡 BUG-3 — مفيش تحقق من «طريقة الدفع» عند الحفظ/الاعتماد (يفشل عند السداد)

| | |
|---|---|
| **الخطورة** | متوسطة (فجوة تحقق) |
| **المكان** | `src/FastCom.Server/Controllers/Finance/ExpensesController.cs` — endpoint الدفع **سطر 516** والتحقق **سطر 535** |

**الوصف:** المستخدم يقدر يسيب «طريقة الدفع» = «— لم يتم التحديد —» وينجح الحفظ وينجح الاعتماد، لكن أول ما يدوس **«تعليم مدفوع»** الـ API يرفض:
```
POST /api/expenses/{id}/pay → 400 {"message":"حدد طريقة الدفع الأول"}
```
يعني الخطأ بيتكتشف في آخر لحظة بدل ما يمنعه من الأول.

**السبب الجذري:** التحقق من `PaymentMethodId != null` موجود فقط في endpoint الدفع (`ExpensesController.cs:535`) — مفيش تحقق مماثل في الحفظ (Create/Update) ولا في الاعتماد (Approve)، ولا في الواجهة قبل الإرسال.

**✅ تصحيح مهم (ملاحظة شفافية):** في التقرير الشفهي الأولي ادّعيت إن الخطأ **بيظهر من غير أي رسالة للمستخدم** — **ده كان غلط وتم التراجع عنه.** اختبار متعمّق (مصروف بدون طريقة دفع + قراءة الـ snackbar كل 200 مللي ثانية) أثبت إن الرسالة بتظهر فعلاً كـ snackbar لمدة ٣+ ثواني:
```
0ms: []   →   200ms: ["حدد طريقة الدفع الأول"]   →   تستمر 3000ms+
```
المصدر: `Expenses.razor` — دالة `SetPaid` (سطر 1579-1588) بتنادي `Snackbar.Add(await MsgOf(res), Severity.Error)` بشكل صحيح.

**الإصلاح المقترح:**
1. تحقق مسبق عند الحفظ: المصروف «مؤكد/مدفوع» لازم يكون له طريقة دفع (سيرفر + واجهة).
2. ترقية طريقة الدفع لـ **حقل إجباري** في خطوة «٢ المحاسبة والدفع» لما النوع يكون نقدي/دفع فوري.
3. تحسين الرسالة لتوضّح مكان الإصلاح: مثلاً «اختار طريقة الدفع في خطوة المحاسبة والدفع قبل السداد».

| | |
|---|---|
| **الخطورة** | منخفضة (تجربة مستخدم) |
| **المكان** | `src/FastCom.Client/Pages/TripForm.razor` — **سطر 2246** |

## ٤. ايه اللي شغال صح؟ ✅

1. **القيود المالية كلها مضبوطة ومتطابقة** — الخزينة = مجموع القيود بالظبط (−600 = −500 −100).
2. **توقيت التقييد صحيح** — المصروف يُقيَّد عند الدفع فقط، العهدة عند الصرف.
3. **الارتباطات (References) سليمة** — كل قيد مربوط بمرجعه `EXP:...` / `CUST-ISSUE:...` وحالته «سارية».
4. فلاتر/مؤشرات شاشة الرحلات (KPI tabs) عربية وصحيحة.
5. رسائل الـ snackbar للنجاح/الخطأ (اعتماد، سداد، حذف) موجودة وشغالة.
6. الحذف بتأكيد مزدوج (زر «حذف؟» inline) وشغال — `DELETE → 200`.
7. الصلاحيات (Admin) سارية على كل الـ endpoints المجرَّبة (`PERM:EXPENSE.VIEW` وغيره).

## ٥. ايه اللي الناقص؟ (لم يُختبر في الجلسة دي)

### ٥.١ وحدات ومسارات **خارج النطاق** — محتاجة اختبار منفصل:
- **التحصيلات والمحفظة** (`/payments`) — إنشاء تحصيل، تطبيق على فاتورة، قيود الخزينة الواردة.
- **الفواتير** (`/invoices`) — إصدار فاتورة من عملية، حالات الفاتورة، الربط بالمصروفات المحمّلة (`BillableAmount`).
- **فواتير ودفعات الموردين** (`/supplier-invoices`, `/supplier-payments`).
- **إغلاق/تسوية العهدة** — إيداع باقي العهدة، إتلاف، إغلاق (Custody Close/Approve) — خصوصًا إن العهدة `CUS-2026-000001` لسه مفتوحة والرحلة لسه في الطريق.
- **إنهاء الرحلة** (Complete) وانعكاسها على المركبة/السائق/التقرير.
- **الحاويات** وأثرها على العمليات.
- **التقارير** (مركز التقارير) — صحة الأرقام مقابل قاعدة البيانات.
- **سجل المراجعة** (Audit) — هل الإجراءات اللي عملناها اتسجلت؟ (لم يُتحقق).
- **الأدوار والصلاحيات** — اختبار بمستخدم غير Admin (كل الاختبارات الحالية كانت ADMIN).
- الإشعارات، المستندات، بوابة العملاء، الإعدادات، البحث العام، المستخدمين، الأسطول/الصيانة، البيانات الأساسية.

### ٥.٢ جوانب تقنية لم تُغطَّ:
- **مفيش اختبارات آلية (Unit/Integration)** — لم يُنفَّذ `dotnet test` في هذه الجلسة؛ الاختبار كان E2E يدوي/آلي فقط.
- **متصفح واحد** (Chromium) — مفيش تحقق من Firefox/Edge/موبايل.
- **RTL/الطباعة/PDF** — لم تُفحص نسخ الطباعة والتقارير المطبوعة.
- **الـ concurrency** — مستخدمين بنفس الوقت على نفس السجل (Race على السداد/القيد مثلاً).
- **الأداء/الحمل** — قوائم كبيرة (مثلاً `take=200` في فورم المصروف — ممكن يبقى ناقصًا لو فيه أكتر من ٢٠٠ رحلة/عملية؛ **ملاحظة مخزنة من دلوقتي**).
- **إعادة المحاولة/انقطاع الشبكة** — سلوك الواجهة لو النت وقع أثناء الحفظ.
- **التواريخ** — تاريخ النظام في الترويسة `02-10-2026` لكن سجلات اتنين اتنشأتوا بتاريخ `05-10-2026` (العهدة والمصروف المدفوع) بينما مصروف اختباري تاني اتنشأ بتاريخ `02-10-2026` — **استحقاق مراجعة**: هل هو فرق timezone بين السيرفر والمتصفح، ولا اختلاف في مصدر التاريخ الافتراضي؟
